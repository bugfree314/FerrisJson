# 大文件感知快开方案：以 1 秒内显示真实内容为目标

建议把“文件已显示”和“文件已完整处理”拆开：**先在 1 秒内显示真实内容并允许基础浏览，完整校验、索引和缓存随后在后台完成。** 首屏不能再依赖整份文件处理结束。

这里的 1 秒是设计目标，目前没有实测依据；磁盘响应、冷启动和文件结构都会影响结果，不能承诺任意文件、任意设备都必达。

**1. 当前打开流程为什么仍然慢**

从源码看，有四处需要调整：

- 默认 GUI 等完整 `Document` 返回后才显示，还会初始化全量展开标记和可见行。
- 稀疏入口先复制完整文件，再开始渐进扫描；有缓存时，首次打开还可能多一次复制。
- 当前早期发布主要针对根数组。根对象、深层数组、首个元素很大的文件，仍可能长时间没有内容。
- 切换文件时，分页树会等待旧任务退休，再启动新任务，旧任务清理也可能拖住首屏。

所以，仅把现有加载函数放到后台，无法解决“用户迟迟看不到文件”的问题。

**2. 用户应该看到的打开过程**

下面是目标时间预算，不是测量结果：

| 阶段 | 时间目标 | 用户看到什么 |
|---|---:|---|
| 接受打开请求 | 立即 | 文件名切换，界面可操作 |
| 首批真实内容 | 尽量 100–300 ms | 文件开头的实际内容、根类型或已识别字段 |
| 首屏可浏览 | 尽量 ≤1 s | 有限树节点，可以选择、展开已发现内容 |
| 后台逐步补全 | 不阻塞前台 | 更多节点可用，已有选择和滚动位置保持 |
| 完整就绪 | 无首屏时限要求 | 完整计数、校验、索引、搜索及查询可用 |

正常后台工作只保留轻量状态提示，不弹进度窗口、不抢焦点。语法错误、读取失败、资源不足仍需要明确显示。

**3. 推荐架构：先读首块，再持续补全**

打开路径调整为：

```text
打开文件
   ↓
优先读取有限首块
   ↓
显示内容片段／初步结构
   ↓
持续读取 → 快照分段写入 → 增量解析 → 发布可用节点
                                  ↓
                           后台索引、校验、缓存
```

关键改动有五项。

**① 首屏只做有限工作**

首批读取建议从 **64 KiB** 起步，首屏最多准备约 **32–64 行**，预览只准备当前可见部分。

不统计全部节点，不计算全部行号，不生成整个根节点的 JSON 预览，也不等待整个根容器闭合。

如果首块不足以形成完整节点，先显示明确标注的内容片段。这样遇到巨型字符串、巨型首条记录时，也能看到真实文件内容，而不是一直空白。

**② 快照复制与扫描改为流水线**

保留稳定快照方向，但取消“整份快照复制完才能扫描”的前置条件：

- 文件按块读取，写入会话专属的追加快照。
- 解析器消费已到达的块。
- 前台只能读取已经发布的快照范围。
- 首屏发布不等待完整缓存写入或持久化检查点完成。

解析器必须区分“暂时没有更多数据”和“文件真正结束”，不能把尚未到达的后半段当作截断错误。

这样可以继续保留快照隔离，同时尽早交付内容。

**③ 增量结构覆盖所有根类型**

不能继续只优化根数组，需要覆盖：

- 根数组；
- 根对象，例如 `{"data":{"rows":[...]}}`；
- 深层嵌套；
- 巨型字符串及巨型首个元素。

为未完成容器明确保存“结束位置未知、子节点总数未知”的状态。已经识别到字段名或容器起点，就可以展示初步结构，不要求先扫描完整个子树。

但这些临时结构不能冒充完整 JSON 值：未闭合节点不能直接完整复制或导出。

**④ 大文件默认使用分页模型**

大文件不再进入需要全量 `Document`、展开标记和可见行数组的旧路径。

建议复用现有分页树引擎，并逐步接入统一的默认界面，保留现有搜索栏、JSONPath 栏和预览操作，避免让用户为了快开文件而切换到另一套实验界面。

小文件可以保留内存后端；分流阈值作为可调整策略，后续由实际表现决定。

**⑤ 新文件首屏不等待旧文件完全释放**

切换文件后：

- 立即取消旧会话的交互请求；
- 旧任务和缓存在后台退休；
- 新文件先使用小额、受预算控制的首屏工作区；
- 大规模后台处理再遵守内存准入。

不能为了快开文件而同时保留两份无界索引；也不能让旧文件释放过程阻塞新文件的少量内容展示。

**4. “后台静默”期间的功能规则**

| 功能 | 文件未完整处理时 |
|---|---|
| 查看内容、滚动 | 已发现范围立即可用，缺页后台请求 |
| 展开、选择、局部预览 | 按需优先处理，不等全文件 |
| 总行数、总元素数 | 显示未知或已发现下界 |
| 跳到尚未发现的位置 | 显示等待，可取消 |
| 完整搜索、JSONPath | 第一阶段保留最新请求，完整验证后执行 |
| 完整复制、导出 | 不输出未闭合节点或冒充完整的结果 |

搜索和 JSONPath 暂时沿用现有完整验证门槛，先集中解决打开与浏览。否则会同时引入部分数组长度、负索引、重复键等语义问题，扩大改动范围。

根对象中的重复键尤其需要明确：扫描中显示的字段值可能被后面的同名字段覆盖，必须标注临时状态并允许更新，不能提前称为最终结果。

**5. 实施顺序**

建议分成五步，每步完成后交给你验收。

| 阶段 | 改动 | 交付结果 |
|---|---|---|
| **G1：首块立即显示** | 独立首屏读取、有限内容预览、旧会话异步退休 | 后台仍在处理时，已经看到真实内容 |
| **G2：流水线加载** | 分段快照、增量输入、发布边界 | 首屏不再等待完整文件复制 |
| **G3：结构逐步可用** | 未完成容器状态、根对象与嵌套发布、按需读取 | 从“看到片段”提升为“尽早浏览结构” |
| **G4：默认入口统一** | 大文件自动使用分页模型，复用当前 UI | 用户正常打开文件就获得快开行为 |
| **G5：后台调度与缓存** | 交互优先、后台限流、延后检查点、缓存后台核对 | 后台补全时保持前台响应 |

其中，**G1 是最快能让用户感知变化的一步，G2–G4 才是完整解决方案。** 不能只做 G1，就宣称大文件已经实现可交互快开。

**6. 如何判断是否真的“快”**

分别记录三个时间，避免把后台任务启动当作首屏完成：

- **首次真实内容显示时间**：用户实际看到文件内容。
- **首次可交互树显示时间**：用户可以选择或展开节点。
- **完整就绪时间**：校验及索引结束。

1 秒目标优先约束前两项。范围继续采用 **100／300／500 MB**，并覆盖根对象、根数组、巨型首条记录、巨型字符串和文件切换；冷启动与程序内打开分别记录。
